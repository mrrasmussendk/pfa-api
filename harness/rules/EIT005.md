# EIT005 — HTTP error bypasses Problem Details
The API answers every error as an RFC 9457 problem document (`application/problem+json` with `type`, `title`, `status`, `detail`, `instance`) — installed once by `create_app()` through `pfa.api.problems.install_problem_details`. FastAPI's own `HTTPException` is a second shape for the same thing: raised from a route it may be converted today, but it carries no problem `type`, cannot carry extension members, and keeps the `{"detail": ...}` vocabulary alive in the code — the next agent copies it, and clients end up parsing two formats. The rule flags any module of the application package outside the features and the kernel (`app_package` in `[tool.eitri]`, default `pfa`: the composition root and the entry points) that imports `HTTPException` from `fastapi` or `starlette` (including `fastapi.exceptions` / `starlette.exceptions`) or reaches it through an attribute chain, with import aliases resolved: `import fastapi as fa; fa.HTTPException(...)`, `from fastapi import exceptions; exceptions.HTTPException(...)` and `import starlette.exceptions as se; se.HTTPException(...)` are all caught. The one module exempt is the one that defines the problem helper (`pfa/api/problems.py`): it must see the framework's exception in order to convert it. Inside a feature the rule does not apply, because a feature may not import the framework at all — there EIT006 speaks, with the remedy that fits.
The remedy the diagnostic names is `problem_helper` in `[tool.eitri]` (default `pfa.api.problems.Problem`), so the rule itself knows nothing about this project.
**Fix:** `raise Problem.domain_rejection(result.error)` for a handler's `Result.ok=False` (422, type `urn:pfa-api:problem:domain-rejection`); for anything else `raise Problem(status, detail, type=..., title=..., **extensions)`. Both come from `pfa.api.problems`. See `harness/guides/returning-errors.md`.
