# EIT005 — HTTP error bypasses Problem Details
The API answers every error as an RFC 9457 problem document (`application/problem+json` with `type`, `title`, `status`, `detail`, `instance`) — installed once by the composition root through `http_common.install_problem_details`. FastAPI's own `HTTPException` is a second shape for the same thing: raised from a slice it may be converted today, but it carries no problem `type`, cannot carry extension members, and keeps the `{"detail": ...}` vocabulary alive in the code — the next agent copies it, and clients end up parsing two formats. The rule flags any slice module that imports `HTTPException` from `fastapi` or `starlette` (including `fastapi.exceptions` / `starlette.exceptions`) or reaches it through an attribute chain, with import aliases resolved: `import fastapi as fa; fa.HTTPException(...)`, `from fastapi import exceptions; exceptions.HTTPException(...)` and `import starlette.exceptions as se; se.HTTPException(...)` are all caught. Inside `contract/` the import is already an EIT003 violation and EIT005 stays silent, so one line yields one remedy. Code outside `src/slices/` (the composition root, `http_common` itself) is not policed — that is where the conversion lives.
The remedy the diagnostic names is `problem_helper` in `[tool.eitri]` (default `http_common.Problem`), so the rule itself knows nothing about this project.
**Fix:** `raise Problem.domain_rejection(result.error)` for a handler's `Result.ok=False` (422, type `urn:pfa-api:problem:domain-rejection`); for anything else `raise Problem(status, detail, type=..., title=..., **extensions)`. Both come from `http_common`, which `internal/routes.py` may import freely (it is not a contract). See `harness/guides/returning-errors.md`.
